# 서울역 여행 미션과 공유방 상태

서울역 COMMONS의 기존 2·3층 지도·시설 사진·보행 경로 위에서 수행하는 게임이다. TRAIN MATES에서 철도블럭을 받고, 철도블럭을 손에 든 채 한정선과 선상통로 계단 앞에서 인증샷을 남긴다. 스토리웨이에서는 구운계란 2개와 칠성사이다 190mL로 구성된 ‘구운란사이’를 본뜬 소품을 얻고, 3층 인생네컷에서는 네 장을 촬영한다. 두 안내부스 앞 역무원 NPC가 미션을 설명한다. 혼자서도 모든 미션을 수행한다. 물건과 스탬프는 게임 내 소품이며 현금 결제·현실 재고·상품 지급과 연결하지 않는다.

## 장소 근거

게임 장소는 `hall.json`의 시설 접근점, `custom.json`의 사진 면과 원래 자산, 등록된 계단 경로에서 찾는다. 자유롭게 만든 좌표로 대체하지 않는다. 8개 상호작용 지점은 실제 충돌 규칙을 적용한 보행 셀이며, 시작점에서 도달 가능한 경로가 있어야 한다. 필수 근거가 사라지면 해당 장소를 임의로 복구하지 않고 게임 초기화를 실패시킨다.

| 장소 | 기준 자료 | 보행 기준 |
|---|---|---|
| 맞이방 안내센터 역무원 | 안내센터 시설·남측 사진 면·기존 관리 자산 | 등록된 2층 접근점 |
| 선상통로 안내부스 역무원 | 안내부스 사진 면·기존 관리 자산 | 사진 정면 방향으로 1.8m 앞을 기준으로 가까운 유효 보행 셀 선택 |
| TRAIN MATES | 굿즈매장 시설·정면/측면 사진·기존 관리 자산 | 등록된 서측 출입 접근점 |
| 한정선 인증샷 | 한정선 시설·기존 승인 사진 면 | 등록된 2층 접근점 |
| 선상통로 계단 인증샷 | `AUTO-F02MV002-1-1`의 실제 모델 이동면 경로 | 선상통로 안내부스 근처의 등록된 2층 계단 하단 |
| 스토리웨이 중앙·서부 | 두 스토리웨이의 기존 시설·접근점 | 등록된 2층 접근점 각각 |
| 인생네컷 | 사진부스 시설·정면 사진·기존 관리 자산 | 등록된 3층 접근점 |

계단 연결은 원본 그래프의 `F02MV002` 모델에서 얻은 17개 중간 이동면을 따라 2층과 3층을 연결한다. 게임은 그 하단과 실제 경로를 그대로 사용한다. 원본 연결의 상태는 `draft`이며 현장 통행 검수 완료를 뜻하지 않는다. 안내부스 접근점이 없던 곳도 사진 면의 위치·정면 방향에서 파생한다. 캐릭터 지점은 건물 안으로 옮기지 않는다. 기존 지형·충돌·층간 이동면을 변경하지 않는다.

## 서버 권위와 수명

공유방은 기존 `/api/commons/join`, `/sync`, `/leave`를 사용한다. 플레이어별 `character`와 `game_state`를 `commons_players`에 보관하며, 마이그레이션 `0003_curly_micromax.sql`이 두 필드를 추가한다. 기본 캐릭터는 `adult-woman`, 허용 캐릭터는 pure 스타일 모듈의 6종 목록이다. 방 호환 버전은 기존 지도·구조·커스텀 데이터 hash에 게임 버전을 덧붙인다. 이전 프로토콜의 방으로 잘못 이어지지 않는다.

입장 응답이 늦는 동안 방을 나가거나 화면을 닫으면 입장을 취소한다. 늦게 도착한 서버 참여자는 퇴장 요청으로 정리하고 연결을 되살리지 않는다. 사진은 열었던 여행의 모드·참여자·세대에 연결한다. 촬영 중 공유방이 만료되거나 다른 방으로 바뀌면 생성한 사진의 저장은 유지하되 다른 여행에 스탬프를 기록하지 않는다.

보상은 서버가 가진 인벤토리와 스탬프로 결정한다. 클라이언트는 게임 상태나 소지품을 덮어쓸 수 없으며 한 번의 행동만 요청한다. 해당 층·3.4m 이내·벽을 통과하지 않는 보행 가능 접근과 이동 중 여부를 확인한다. 두 인증샷에는 획득한 철도블럭을 실제 소지 상태로 장착해야 한다. 인생네컷 요청은 네 장을 촬영한 상태여야 한다. 이미지 파일 생성·다운로드는 브라우저에서 수행하며 서버에 인증샷 원본을 업로드하지 않는다. 서버의 사진 검증은 전달받은 장수와 장소·소지품 조건에 대한 것으로, 렌더링한 이미지 내용을 판독하지 않는다.

수락한 행동은 요청 ID와 내용으로 중복을 판정한다. 같은 요청의 재시도는 보상을 다시 주거나 이후 소지 상태를 되돌리지 않는다. 같은 ID의 다른 내용은 거부한다. 기록은 방 안에서 플레이어별 최대 1,024개로 제한한다. 위치 동기화의 순번도 함께 검사하므로 동시 요청이 보상을 중복 기록하지 않는다. 응답을 잃은 재전송에는 최신 서버 상태로 회복한다.

게임 조건만 실패한 경우 정상적인 이동·캐릭터·순번은 반영하고 `422`와 게임 오류·최신 상태를 반환한다. 보행 경로·속도·등록된 층간 연결, 인증·만료 오류는 기존 이동 검증을 따른다. 유효한 등록 보행점으로의 기존 위치 이동은 유지하지만, 위치를 옮기는 같은 요청에서 미션 보상까지 받을 수는 없다. 계단 이동 중에는 실제 등록 경로로 캐릭터가 이동하며 소지품 상태도 유지한다.

다른 플레이어에게는 캐릭터·현재 소지품과 기존 위치·자세·층간 이동 표시만 보낸다. 인벤토리·스탬프·행동 기록·인증 토큰은 공유하지 않는다. 소지품은 매장 밖에서도 유지된다. 공유방은 기존 20분 수명·20초 무응답 만료·20명 정원을 따르며 별도 계정 영속 보관을 추가하지 않는다. 솔로 진행과 공유방의 개인 진행은 분리하여, 클라이언트 소지품을 서버로 가져와 보상받지 않는다.

## 검증

- `node tools/test-commons-game.mjs`: 8개 장소의 근거·보행점·도달 경로, 사진 정면에서 파생한 안내부스 위치, 등록 계단 이동면, 벽·층·이동 중 검증, 솔로 전체 미션, 두 소품과 장착, 원격 캐릭터·휴대 표시, 게임 전용 오류의 순번 반영, 재시도·동시 요청·다른 내용 충돌, 네 장 조건, 초대방·인증·프로토콜·정확한 만료 경계, 지도와 업무 데이터 불변을 실제 메모리 SQLite API로 확인한다.
- 기존 `tools/test-commons.mjs`의 보행·충돌·경로·속도·정원·동기화·만료 회귀를 유지한다. 테스트에서 바뀐 스냅샷 필드는 `character`, `heldItem`이며, 인벤토리는 계속 비공개다.
- `node tools/test-commons-avatars.mjs`: 여섯 캐릭터와 역무원 복장, 캐리어·철도블럭·계란 두 개/사이다 소품, 32명 표시 한도, 유효한 애니메이션 행렬, 네 번의 독립 렌더/복사, 촬영 뒤 카메라·상태 복원과 자원 해제를 확인한다.
- `node tools/test-commons-journey-client.mjs`: 같은 요청 ID·순번으로 재시도, 게임 오류의 정상 이동 확인, 원격 캐릭터·소품, 늦은 입장 응답의 퇴장/종료 후 연결 부활 방지, 네 번의 촬영·중단, 촬영 중 모드 만료·방 교체 후 보상 격리와 사진 유지, 두 역무원 NPC의 유효 보행점·여행자와의 간격을 확인한다. 합성 캔버스 fixture로 각 프레임의 독립된 원본 참조와 종횡비 보존을 검증한다.
- `node tools/test-commons-journey-dom.mjs`: 실제 여행 UI를 합성 DOM에서 실행해 같은 공유 상태·결과 영수증만 바뀐 응답에서는 미션/가방 버튼과 키보드 초점을 유지하고, 진행·장착·여행 모드가 바뀌면 화면을 갱신함을 확인한다.

사진 출력은 원본 전체를 종횡비에 맞춰 담는 가로 720px PNG다. 인증샷 한 장 또는 서로 다른 네 순간을 세로로 묶은 네컷을 저장하며, 네컷 합성 크기는 720 × 1898px다. 촬영 결과를 서버에 업로드하거나 실제 카메라 장치로 촬영하지 않는다.

최종 서비스 통합 검사에서는 위 다섯 검사 묶음과 `npm run build`, `npm run test:collab`이 통과했다. 빌드에는 기존 설정 파일의 공개 Supabase 환경값 두 개만 주입하고 값을 출력하지 않았다. 빌드가 생성한 `message.webp`는 실행 전 바이트로 보존했다. 기존 협업 빌드 검사에는 역 변경 로더의 이전 함수명 `loadToolkitOverlays`를 찾는 기준선 오류가 있었으므로, 현재 `loadToolkitChanges(siteId)`의 정의와 현재 역을 인자로 사용하는 호출을 확인하도록 수정했다. 공개 API·이미지·렌더링 등의 다른 검증 조건은 유지했다.

순수 규칙/API 테스트는 브라우저 사진 다운로드나 최종 렌더링의 시각 품질을 대신하지 않는다. 실제 화면의 캐릭터·소품·촬영·다중 탭 동기화는 별도 통합 검증으로 확인한다. 새 포트·전역 패키지·상품 결제·채팅·운영 배포는 이 작업에 추가하지 않는다.
